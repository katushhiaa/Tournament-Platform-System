# Data Integrity & Storage Mechanisms

Цей документ описує механізми збереження даних, підтримки їх цілісності та узгодженості, які імплементовані на рівні бази даних PostgreSQL в проекті **Tournament Platform System**.

---

## 1. Primary Keys (Первинні ключі)
В якості первинних ключів у системі використовується тип `UUID`. 
Для генерації унікальних ідентифікаторів безпосередньо в базі даних використовується вбудована функція `gen_random_uuid()`. 
Використання UUID гарантує глобальну унікальність записів та ускладнює їх перебір зловмисниками (на відміну від послідовних цілих чисел).

## 2. Foreign Keys (Зовнішні ключі) та Каскадні операції
Зовнішні ключі забезпечують реляційну цілісність даних (Referential Integrity). Якщо об'єкт видаляється, пов'язані з ним залежні дані обробляються згідно з чіткими правилами:

### 2.1 Cascade Delete (Каскадне видалення)
Використовується для тісно пов'язаних сутностей, де існування дочірнього запису не має сенсу без батьківського:
* **Користувач (User):** При видаленні користувача (Hard Delete) автоматично видаляються його деталі (`USER_DETAILS`), телефони (`USER_PHONE`), преференції (`USER_TOURNAMENT_THEME_PREFERENCE`) та токени сесій (`REFRESH_TOKEN`).
* **Турнір (Tournament):** При видаленні турніру видаляються всі команди (`TEAM`), що брали в ньому участь, та згенеровані матчі (`MATCH`).
* **Команда (Team):** При видаленні команди, каскадно видаляються записи про участь користувачів у ній (`USER_TEAM`).

### 2.2 Set Null (Встановлення значення NULL)
Використовується, коли сутність може продовжувати існувати навіть після видалення пов'язаного об'єкта:
* **Організатор турніру:** Якщо акаунт організатора видаляється, поле `organizer_id` в таблиці `TOURNAMENT` стає `NULL`. Турнір залишається в системі для історії.
* **Учасники матчу:** Якщо команда видаляється, відповідні поля в таблиці `MATCH` (`team_a_id`, `team_b_id`, `winner_id`) встановлюються в `NULL`.

### 2.3 Restrict (Заборона видалення)
* **Стан акаунту (Account State) та Теми (Themes):** Видалення системних довідників (наприклад, статусу "active" або теми "Chess") заборонено, якщо на них є посилання з існуючих таблиць.
* **Match:** Заборонено видаляти команду з турніру, якщо вона є `team_a_id` в будь-якому матчі.

## 3. Unique Constraints (Унікальні обмеження)
Унікальні обмеження запобігають дублюванню критичних даних:
* **User Details:** Унікальність `email` (один email = один акаунт) та `user_id` (зв'язок 1:1 з таблицею User).
* **Teams:** Унікальна пара `(name, tournament_id)` гарантує, що в рамках одного турніру не може бути двох команд з однаковою назвою.
* **Matches:** Комбінація `(tournament_id, level, order_number)` є унікальною. Це захищає від дублювання позицій матчів у турнірній сітці.
* **User Team:** Унікальна пара `(user_id, team_id)` не дозволяє користувачу приєднатися до однієї команди двічі.
* **Dictionaries:** Унікальні назви статусів (`account_state.name`) та тем турнірів (`tournament_theme.name`).

## 4. Soft Deletes (М'яке видалення)
Для критичних сутностей застосовується механізм "м'якого видалення" задля збереження історії (наприклад, для турнірної статистики) або можливості відновлення:
* **User & User Phone:** Поле `deleted_at`. Запис фактично залишається в БД, але фільтрується на рівні додатку. Це дозволяє зберігати зв'язок зіграних матчів із користувачем, навіть якщо він "видалив" свій профіль (GDPR compliance).
* **Team:** Поле `is_disqualified`. Команди не видаляються з турніру в разі порушення правил, а позначаються як дискваліфіковані.
* **Match:** Поле `is_valid`. Матчі не видаляються, а можуть бути позначені як недійсні (наприклад, через перегляд результатів).

## 5. Check Constraints (Обмеження значень)
*(Частина перевірок реалізована на рівні application-шару через Entity Framework та валідатори, але БД підтримує такі логічні перевірки через типи даних)*:
* Переможець матчу (`winner_id`) має обов'язково бути однією з команд-учасниць матчу.
* Значення для оцінок (`team_a_score`, `team_b_score`) за замовчуванням дорівнюють `0`.

## 6. Timestamping (Історичність змін)
Більшість таблиць мають поля `created_at` та `updated_at`:
* `created_at` заповнюється автоматично на рівні бази даних (`DEFAULT CURRENT_TIMESTAMP`).
* `updated_at` оновлюється при кожній модифікації запису.

## 7. Indexes (Індекси)
Для оптимізації швидкості виконання запитів на зовнішні ключі та поля, за якими найчастіше відбувається пошук або фільтрація, створені B-Tree індекси:
* Всі поля зовнішніх ключів (FK), наприклад: `tournament_id` у таблицях `team` та `match`.
* Поля для пошуку: `email` у `user_details`, `token` у `refresh_token`.
* Поля статусів: `status` у `tournament`, `deleted_at` у `user` для швидкого відфільтровування видалених об'єктів.
